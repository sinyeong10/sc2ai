# 스타1(브루드워) 빌드 최적화 설계 (2026-11-08)

스타2 python-sc2 봇으로 풀던 "질럿 N기 최단 생산"을 스타1로 옮긴다. 구조는 사용자가 정한 대로
**AI는 Python(학습 PC), 실행기는 C++(게임 PC), 명령은 TCP로 다른 PC에서** 내린다. 이 문서는
(1) 실행기가 가져야 할 자동 기능 목록, (2) 스타1을 돌리는 방법들의 조사·코드 분석 요약과 선택,
(3) 방식만 바꿔 같은 명령을 내리는 공통 계층의 설계와 현재 구현 상태를 적는다.

조사 원문(출처·`파일:줄` 인용 포함): [docs/스타1-조사/](스타1-조사/)의 `BWAPI-조사.md`, `OpenBW-조사.md`,
`브리지-TorchCraft-BOSS-조사.md`. 모두 소스를 읽기만 했고 빌드·실행은 하지 않았다. 각 항목에 **[확인]**(소스·공식 문서)과
**[추정]**이 표시돼 있다.

> **스타1 작업 전에 먼저 볼 공식 자료** (사용자 지정, 2026-11-08)
> - BWAPI API 문서: https://bwapi.github.io/ — AI 모듈 콜백은 [AIModule 클래스](https://bwapi.github.io/class_b_w_a_p_i_1_1_a_i_module.html)
>   (`onStart`, `onFrame`, `onUnitComplete` 등 `bridge/cpp`가 구현하는 인터페이스)
> - BWAPI 릴리스: https://github.com/bwapi/bwapi/releases — 런타임 `BWAPI_Setup.exe`는 여기서 받고, 버전은 서브모듈 태그(v4.4.0)와 맞춘다
>

## 0. 결론

- **실행기는 하나의 C++ BWAPI AI 모듈**로 만들고, 같은 소스를 **(a) 스타1 1.16.1 + BWAPI 4.4.0(Windows DLL)** 과
  **(b) OpenBW + OpenBW/bwapi 포크(Linux `.so`, 헤드리스)** 두 호스트에서 빌드한다. Remastered는 공식 경로가 없다.
- Python 브리지(pybrood, PyBW 등)는 전부 죽었고 BWAPI 클라이언트 모드(공유 메모리)는 같은 PC 전용이라, **원격 PC는
  게임 프로세스 안에 소켓 서버를 두는 TorchCraft 방식이 유일**하다. 그대로 따르되 의존성 없는 JSON 줄 TCP로 줄였다.
- Python 쪽은 `bridge/env.py`의 `make_env(이름)` 하나로 시뮬레이터·원격 실행기를 바꾼다. 시뮬레이터 실행기를 TCP로
  붙여 왕복 시험을 통과했다. **C++ 모듈은 이 환경에 툴체인과 게임이 없어 컴파일·실행을 확인하지 못했다.**
- 결정론을 위해 **프레임 블로킹**(명령을 기다리는 동안 게임 프레임을 멈춤)과 **시드 고정**(1.16.1은 `seed_override`,
  OpenBW는 `setRandomSeed`)을 프로토콜 요구사항으로 넣었다. SC2에서 노이즈 출처로 의심한 일꾼 배분·건설 위치는 결정론 규칙으로 바꿨다.

## 1. 문제 정의가 스타1에서 바뀌는 것

| 항목 | 스타2(지금까지) | 스타1 프로토스 |
|---|---|---|
| 시작 상태 | 미네랄 50, 일꾼 12, 인구 12/15 | 미네랄 50, 일꾼 4, 넥서스 인구 9 (BOSS는 8로 적음. 게임에서 확인) |
| 파일런 | 100, +8 | 100, +8 |
| 게이트웨이 | 150, 완성 파일런 필요 | 150, 파일런 전력 범위 필요 |
| 질럿 | 100, 인구 2 | 100, 인구 2 |
| 시간 증폭 | 넥서스 에너지 | 없음 → 시뮬레이터의 chrono 항 3개가 사라진다 |
| 시간 단위 | 봇 iteration(≈5.5 게임 루프) | 게임 프레임 (fastest 약 23.8 fps). 생산 시간 프로브 300, 파일런 450, 게이트 900, 질럿 600 프레임(게임 데이터, 실행으로 확인 필요) |
| 인구 표기 | 1 단위 | 내부 2배 단위. 실행기가 2로 나눠 보냄 |
| 상대 | 컴퓨터(공격 없음, Simple64) | 1.16.1 컴퓨터는 공격해 옴 → 맵·종족 선택 필요. OpenBW는 컴퓨터 AI가 없어 가만히 있음 |

열거 규칙(`1.backtrack-all-action.py`)과 행동 마스크의 상수(일꾼 12 시작, 한도 15, 미네랄 패치 8)는 스타1 값으로 매개변수화해야
한다. `offline_rl/build_sim.py`의 구조(수입·대기·스케줄)는 그대로 쓰되 chrono 항을 빼고 상수를 다시 적합한다. BOSS의 결정론
시뮬레이터 상수(일꾼당 0.045 미네랄/프레임, 건물 배치 여유 120프레임, 대기 조건 6개의 max)가 첫 어림값과 단위 시험 기준이 된다.

## 2. 실행기가 가져야 할 자동 기능 (환경의 일부, 명령이 아님)

readme의 설계대로 AI는 4가지 명령만 내리고 나머지는 실행기가 알아서 한다. 상태 공간을 줄이기 위한 의도적 선택이며, 규칙을 바꾸면
로그와 시뮬레이터 적합값이 달라지므로 규칙을 문서에 고정한다. `bridge/cpp/src/BuildExecutor.h` 머리말의 A1~A9와 같다.

| # | 기능 | 규칙 | SC2 봇과의 차이 | 구현 |
|---|---|---|---|---|
| A1 | 일꾼 자동 채취 | 넥서스 반경 안 미네랄 패치를 거리순으로 정렬, 일꾼을 ID순으로 라운드로빈 배정(패치당 2명까지 우선). 새 프로브는 가장 적게 배정된 패치로. 놀고 있으면 자기 패치로 `gather` | python-sc2 `distribute_workers()`는 매 프레임 비결정적 | `assignMinerals`, `autoMine`, `onUnitComplete` |
| A2 | 건설 일꾼 선택 | 미네랄을 들고 있지 않고 건설 중이 아닌 프로브 중 목표 타일에 가장 가까운 것. 건물을 놓은 뒤 놀면 A1이 되돌림 | `build()`가 내부에서 고름 | `pickBuilder` |
| A3 | 건설 위치 | 파일런: 넥서스→적 본진 방향 5타일(첫), 7타일(이후) 기준점. 게이트: 첫 완성 파일런 기준점. 기준점에서 결정론적 나선 탐색으로 `canBuildHere`·`hasPower` 통과하고 미네랄 길을 막지 않는 첫 타일 | 3, 5~7 무작위 | `findBuildTile` |
| A4 | 생산 건물 배정 | 완성 게이트 중 큐가 가장 짧고, 같으면 남은 생산 시간이 가장 적은 것. 넥서스 큐는 5까지 허용 | 첫 완성 게이트 큐 + 빈 게이트로 재분배(결과는 같음) | `pickGateway` |
| A5 | 실행 가능 판정과 대기 | 자원 ≥ 비용, 인구 여유, 선행 건물 완성, 일꾼·위치 확보가 모두 되는 **첫 프레임**에 명령을 내리고 그 프레임을 기록. 선행 건물이 아예 없으면 즉시 실패(`fatal`), 있지만 미완성이면 대기 | `finish_action`과 같음 | `tryExecute` |
| A6 | 건설 확인·재발행 | 명령 뒤 일꾼이 놀거나 600프레임 안에 건물이 생기지 않으면 같은 명령을 다시 내림(새 명령 아님, 로그에 안 찍힘). 40회 넘으면 포기 | 없음(그래서 유실 가능성이 있었음) | `BuildWatch`, `checkBuildWatches` |
| A7 | 종료 판정 | 목표 수째 질럿 **완성 이벤트** 프레임 = `end_frame`. 마지막 질럿 명령의 응답은 완성까지 미룸 | 다음 iteration에 기록(+약 12) | `onUnitComplete`, `awaitingEnd` |
| A8 | 에피소드 재시작 | `reset` → 1.16.1은 `restartGame()`(싱글 전용), OpenBW는 `leaveGame()` + 런처 `auto_restart`. `onStart`에서 상태 초기화 | 프로세스·소켓 재생성 | `wantRestart_` |
| A9 | 속도·결정론 | `setLocalSpeed(0)`, `setGUI(false)`, 사운드 OFF, 프레임 블로킹, 시드 고정 | iteration 기반 | `setupSpeed`, `onFrame` 대기 루프 |
| A10 | 관측·로그 | 명령 실행 시점의 10칸 state(SC2 로그 호환)와 `extra`(완성 게이트 수 등)를 응답하고 JSON 줄로 파일에 남김 | pickle 파일 | `obsJson`, `logObservation` |
| A11 | 오류 처리 | 명령 거부(`getLastError`)는 재시도, 선행 조건 불가능은 `accepted=false`로 에피소드 종료, 클라이언트 끊김은 대기 명령 폐기 | 소켓 b"" 문제 | `handleMessage`, `finishPending` |

추후 가스·사이버네틱스 코어·드라군(행동 4·5·6)을 더할 때는 A1에 가스 일꾼 3명 배정(UAlbertaBot `WorkersPerRefinery=3`)과
A5의 선행 조건 표만 늘리면 된다. 행동 번호는 재사용하지 않는다.

### 코드 분석에서 가져온 것

- **BWAPI 서버가 클라이언트 응답을 기다리며 프레임을 멈춘다**(`bwapi/BWAPI/Source/Server.cpp:737-753`). 우리 모듈은 `onFrame`에서
  다음 메시지를 기다려 같은 효과를 낸다. 이것이 없으면 AI의 생각 시간이 게임 시간이 된다.
- **AI 모듈 선택 순서와 진입점**(`GameUpdate.cpp:333-396`, `Dll.cpp`의 `gameInit`/`newAIModule`). OpenBW 포크는 `.so`를
  `dlopen`으로 같은 심볼을 찾는다(`GameUpdate.cpp:417-452`) → 소스 하나로 두 호스트.
- **OpenBW 런처 루프**(`BWAPILauncher/Source/Main.cpp`): `startGame → {update; nextFrame} → onGameEnd → leaveGame`을
  `auto_restart != OFF`인 동안 반복하고 MPQ는 다시 읽지 않는다. 설정은 `BWAPI_CONFIG_<섹션>__<키>` 환경 변수로 준다.
- **TorchCraft 컨트롤러**(`BWEnv/src/controller.cc:712-912`): 프레임 상태 전송 → 명령 수신 → 같은 프레임에 `issueCommand`
  → 다음 프레임에 명령별 상태 반환. 우리 프로토콜의 `accepted`, `latency_frames`, `wait`가 여기서 왔다.
- **BOSS**(`ualbertabot/BOSS`, MIT): 스타1 결정론 빌드 시뮬레이터 + 탐색. `whenCanPerform = max(선행, 미네랄, 가스, 라바, 인구, 일꾼)`
  (`GameState.cpp:475-515`), 일꾼당 수입 선형(`:923-931`), 건물 배치 여유 120프레임(`UnitData.cpp:166`). 우리 `build_sim.py`의
  `earliest_afford`·`supply_time`과 같은 분해다. SC1 시뮬레이터의 초기값과 단위 시험으로 쓴다.
- **UAlbertaBot**의 `ProductionManager`/`WorkerManager`/`BuildingPlacerManager`, **TorchCraftAI**의 `gatherer`, `builderhelper`
  는 A1~A4의 검증된 구현이다. 지금은 직접 짠 단순 규칙을 쓰고, 실게임에서 문제가 나오면 이쪽을 참고한다.

## 4. 공통 계층 아키텍처

```
학습 PC (Python)                         게임 PC (C++ 또는 Python)
┌──────────────────────────┐             ┌──────────────────────────────┐
│ offline_rl / 학습 코드    │             │ 1.16.1 + BWAPI: BuildExecutor.dll │
│   env = make_env("openbw")│ ──TCP/JSON──► OpenBW: libBuildExecutor.so      │
│   obs = env.reset(5)      │   protocol  │ 시험: executor_sim.py (BuildSim)   │
│   obs = env.step(a)       │   v1        │ (예정) python-sc2 봇 실행기          │
└──────────────────────────┘             └──────────────────────────────┘
         ▲ 같은 코드                                 ▲ 같은 메시지, 같은 의미
```

- **프로토콜** [bridge/protocol.md](../bridge/protocol.md): JSON 한 줄 TCP, `hello/reset/step/stop/status/bye`,
  응답 `obs/wait/error`. `step`은 명령이 실제로 내려진 프레임까지 막힌다(로그 한 줄 = 명령 실행 시점 관측 규약 유지).
  `id` 재전송 안전, 프레임 블로킹, 마지막 명령은 완성까지 응답 보류, 10칸 `state`는 기존 로그와 호환.
- **Python** [bridge/env.py](../bridge/env.py): `BuildEnv`(reset/step/close), `SimBackend`, `RemoteBackend`, `make_env(이름)`.
  백엔드 목록은 [bridge/backends.example.json](../bridge/backends.example.json)(복사해 `backends.json`으로, 주소만 바꾼다).
- **참조 실행기** [bridge/executor_sim.py](../bridge/executor_sim.py): 시뮬레이터를 같은 프로토콜로 내놓는 서버. C++ 쪽이
  따라야 할 메시지 처리 순서의 기준이고, 게임 없이 원격 경로를 시험한다.
- **C++ 실행기** [bridge/cpp/](../bridge/cpp/): `BuildExecutor`(자동 기능 + 프로토콜), `TcpLineServer`(읽기/쓰기 스레드와
  게임 스레드를 큐로 분리, 게임 스레드는 소켓에서 안 막힘), `MiniJson`(의존성 없음), `Dll.cpp`, CMake(Windows/OpenBW 분기),
  `bwapi.ini.example`, README(확인된 사실과 코드 대응표).

왜 ZMQ·FlatBuffers가 아니라 JSON 줄인가: 메시지가 에피소드당 수십 개, 한 개 수백 바이트라 직렬화 비용이 무의미하고, 게임 PC(특히
OpenBW를 올릴 소형 보드)에 라이브러리를 깔지 않아도 되며, 디버그가 `nc`로 된다. 볼트의 [[ZMQ-브로커로-프로세스-간-JSON-RPC-구현]]이
말하는 "공통 메서드(`status`)를 공용으로, 핸들러 예외를 수신 루프에서 잡기"와 [[모션-명령-큐와-완료-보고]]의 "같은 ID 재전송은 갱신이지
재실행이 아니다", "시작 전 침묵에 상한"을 그대로 따랐다(`wait` 생존 신호, `id` 중복 처리).

## 5. 결정 기록

| 결정 | 이유 | 대안과 버린 이유 |
|---|---|---|
| 실행기를 AI 모듈(DLL/.so)로, 클라이언트 EXE가 아니라 | 클라이언트 모드는 같은 PC 전용이고 OpenBW에서 "not supported" | 클라이언트 EXE + 소켓: Windows만 됨 |
| 1.16.1을 1차, OpenBW를 2차 | 1.16.1이 원본 수치. OpenBW는 리눅스·헤드리스·시드·스냅샷이 좋지만 라이선스 없음, 수치 일치 미검증, ARM 증거 없음 | OpenBW만: 검증 기준이 없어짐 |
| **지금은 BWAPI(Windows)만 빌드, OpenBW는 서브모듈 등록만** (사용자 결정, 2026-11-08) | 작업 PC가 Windows라 OpenBW 빌드(Linux 툴체인, MPQ, 포크 설치)까지 가는 것은 1차 검증에 불필요. 소스는 `third_party/`에 고정해 두고 1.16.1 결과가 나온 뒤 돌아온다 | 둘 다 빌드: 검증 기준(1.16.1)이 없는 상태에서 비교 대상만 늘어남 |
| BWAPI 소스를 서브모듈 `third_party/bwapi`(태그 v4.4.0)로 | 4.4.0은 미리 빌드된 lib 없이 BWAPILIB 소스를 함께 컴파일하므로 소스 자체가 빌드 입력. CMake 기본값이 이 경로 | SDK zip 수동 설치: 버전 추적 안 됨 |
| 프레임 블로킹을 프로토콜 요구사항으로 | 결정론 가정(명령열 → 결과)이 전제. AI 지연이 섞이면 로그 재현 불가 | 비블로킹 + 타임스탬프: 재현 불가 |
| 명령 실행 시점에 응답, 건설은 별도 감시 | SC2 로그 규약과 같아 `offline_rl` 코드 재사용. 건물 유실은 A6이 막음 | 건물 놓일 때 응답: 로그 의미가 바뀜 |
| 마지막 질럿은 완성까지 응답 보류 | `SimBackend`와 의미를 맞춰 AI 코드가 분기하지 않게 | 별도 `done` 폴링: 복잡 |
| JSON 줄 TCP, 인증 없음 | 위 4절. LAN/SSH 터널 전제 | ZMQ/gRPC: 의존성 |
| 자동 기능을 직접 짬(단순 규칙) | 결정론과 문서화가 우선. 검증된 구현(UAlbertaBot 등)은 문제 생기면 참고 | BWEM/BWEB 도입: 의존성·빌드 부담 |

실게임에서 처음 할 검증 순서:

1. Windows에 1.16.1 설치본 + VS2017 Build Tools(v141_xp, Win32) + CMake를 준비하고
   `git submodule update --init third_party/bwapi` → `cmake -S bridge/cpp -B build-win -A Win32` → `cmake --build build-win --config Release`로
   `BuildExecutor.dll` 빌드. `bwapi.ini.example`을 적용하고 `BUILD_EXEC_GUI=1`로 한 에피소드를 눈으로 본다(일꾼 배정, 파일런·게이트 위치, 질럿 완성 프레임).
2. 다른 PC에서 `make_env("bwapi-win")`으로 `[1,2,2,2,3,3,3,3,3]`(N=5)을 10번 돌려 종료 프레임 분산을 잰다.
   SC2의 중앙값 5·최대 50보다 작아야 결정론 규칙이 효과가 있는 것이다. `seed_override`를 바꿔 가며 시드 영향도 본다.
3. 같은 명령열을 OpenBW에서 돌려 프레임 차이를 잰다. 차이가 몇 프레임 안이면 OpenBW를 대량 실행에 쓴다.
4. 열거 규칙을 SC1 상수로 바꿔 N=2 전수(수백 개)를 1.16.1에서 돌려 로그를 만들고, `build_sim.py`를 재적합해 BOSS 상수와 비교한다.

## 7. 열린 질문과 위험

- **1.16.1 바이너리 입수**와 라이선스. OpenBW는 1.16.1의 MPQ 3개가 필요하다(Remastered CASC 미지원).
- **OpenBW 엔진 저장소에 LICENSE가 없다**(issue #17, 2018~). 공개 배포물에 넣으려면 확인이 필요하다.
- **ARM 보드에서 OpenBW**는 근거가 없다(x86 고유 코드도 없음). 빌드해 봐야 안다. 22k줄 단일 헤더 컴파일 메모리가 소형 보드의 병목일 수 있다.
- 1.16.1 컴퓨터 상대의 공격을 피하는 맵·설정. UMS 맵이나 상대 없는 설정이 가능한지 확인.
- `onUnitComplete`가 시작 유닛에 오는지, OpenBW 포크(4.2.0)에 `setCommandOptimizationLevel`·`getFPS`가 있는지.
- 넥서스 시작 인구(9 vs BOSS의 8), 프로브 큐 적재 시 자원 차감 시점, 파일런 전력 범위가 게이트 배치에 미치는 제약.
- 프레임 블로킹 중 Windows 메시지 루프가 멈추는지(창 응답 없음 표시). `blockTimeoutMs_` 50ms 루프라 실제 멈춤은 없지만 확인.
