## 2. 문제 정의 (정리된 형태)

- 초기 조건 고정(Simple64, 프로토스, 멀티 없음), 행동 4개(0 일꾼, 1 파일런, 2 게이트, 3 질럿), 목표 질럿 N기 완성 프레임 최소화.
- 결정은 **직전 명령이 "끝났을 때"** 내린다. 단, "끝남"의 뜻이 다르다. 유닛은 생산 완료, 건물은 **건설 명령을 일꾼에게 준 순간**이다. 그래서 게이트 명령 직후 다음 결정에서는 관측값에 게이트가 아직 없다(42%). 질럿 명령은 봇이 준비된 게이트를 기다려 주므로 그 대기 시간이 질럿 명령의 비용에 들어간다.
- 명령 순서가 정해지면 결과가 (거의) 정해진다. 같은 명령열을 다시 돌리면 종료 프레임이 중앙값 5, 최대 50 흔들린다. 이 흔들림은 전제로 받아들이고 평균으로 비교한다.
- 편의 조건(실행 계층에 고정된 것): `distribute_workers`로 일꾼 자동 배분, 유휴 게이트에 질럿 자동 분배 + 시간 증폭, 건설 위치·건설 일꾼은 라이브러리 기본값, 자원·선행 건물 부족 시 봇이 대기, 가스·멀티·코어 없음, 질럿 뒤 일꾼 생산 금지(열거 규칙). 찾은 최적은 **이 조건 아래의 최적**이다.

## 3. 결정 기록

| 결정 | 이유 |
|---|---|
| 감가율을 쓰지 않는다 (γ=1) | 명령 수가 많아도 더 빠를 수 있다. readme에 이미 있던 판단이며 실험으로 확인. |
| 보상은 명령마다 `-소요 프레임` | 종료 시 지수 보상 하나보다 안정적(583±4 → 575±0.4). 최적 정책은 같다. 시간을 비용으로 보는 SMDP 관점. |
| 불가능한 행동은 종료+음수 보상 대신 선택지에서 제거(action masking) | readme 7번의 "음수 보상이 이전 상태로 번져 빠른 경로를 안 간다" 문제가 생길 여지가 없다. |
| 학습률은 고정 0.1 | 1/n은 부트스트랩 목표가 바뀌는 동안 초기의 낙관적 값을 오래 남겨 느렸다(627 대 575). |
| 상태는 명령열(history)을 기준으로 삼는다 | 추상화 손실이 없어 최적에 +3.7프레임까지 접근. 단, 질럿 5기 이상으로 커지면 더 작은 상태가 필요. |
| 관측값 기반 상태는 쓰지 않는다 | 건설 중 건물이 안 보여 "게이트 없이 질럿"을 최적으로 학습한다. 쓰려면 "진행 중 건설(개수, 남은 시간)"을 넣어야 한다. |
| 명령 횟수 상태(semi_world 방식)는 보조로만 | 같은 횟수에 다른 순서로 도달한 경우가 섞여 정확해(가치 반복)로도 최적보다 35프레임 손해. |
| 봇을 "건물 완성까지 대기"로 바꾸지 않는다 | 최적 명령열이 게이트 건설 중 일꾼을 뽑는 겹치기다. 대기시키면 겹치기가 사라진다. |
| 목표가 다른 문제(질럿 2 → 5)로 옮기는 수단은 표가 아니라 **시뮬레이터(비용 모델)** | 질럿 5의 11번째 이후 결정 상태는 질럿 2 데이터에 0%다(6.5절). 옮길 수 있는 것은 "명령이 얼마나 걸리는가"의 규칙뿐. |
| 시뮬레이터 수치는 질럿 2 로그로만 적합하고 질럿 5 로그는 검증에만 쓴다 | 구조(규칙)는 봇 코드에서 가져오고 수치만 학습. 검증 데이터를 보고 고친 구조 3가지는 6.5절에 기록. |
| 인구수 규칙: 일꾼은 명령 즉시, 질럿은 생산 시작 시 차지 | 로그 관찰: 일꾼 3기 명령 뒤 4기째가 파일런 완성을 기다림. 게이트 1개에 질럿 3기 명령 뒤 supply_used=16. 두 규칙이 다른 이유는 미확인(열린 질문). |

읽는 법:
- history 상태의 Q-learning이 전수 열거(4,805개 명령열)와 같은 답을 20만 에피소드로 찾았다. 에피소드 수는 명령열 수의 약 40배라 열거보다 적지는 않지만, 질럿 2기에서 +3.7이던 격차가 5기에서는 0이 됐다.
- 학습 곡선은 16만 에피소드까지 840~875에 머물다 18만에서 723으로 떨어진다. Q를 0으로 시작하면 보상이 모두 음수라 아직 안 가본 행동이 항상 더 좋아 보여, 1만 개 상태를 전부 훑기 전까지 탐욕 정책이 미방문 경로를 택하기 때문이다. 수렴에 필요한 에피소드 수는 상태 수에 비례하므로, 상태를 줄이는 것이 곧 학습 비용을 줄이는 길이다.
- 보상 설계 차이는 2기(583 대 575)보다 5기(758 대 723)에서 뚜렷하다. 종료 시 보상 하나로는 10개 명령 중 어느 것이 시간을 잡아먹었는지 알 수 없어 긴 문제에서 더 불리하다.
- cmd_counts의 손해는 2기 +35 → 5기 +110~183으로 커졌다. 명령열이 길어질수록 "같은 횟수, 다른 순서"가 많아져 뭉개짐이 심해진다. 이 상태 표현으로는 규모를 키울 수 없다.
- 5기 최적 `[1,2,2,2,3,…]`은 2기 최적 `[1,2,2,0,3,…]`과 앞 세 명령(파일런, 게이트, 게이트)이 같고 네 번째에서 갈린다. 5기는 게이트 3개를 먼저 짓고 일꾼을 전혀 뽑지 않는다. 목표가 달라지면 접두사만 공유되므로 goal-conditioned 상태가 필요하다.
- 질럿 명령 뒤 일꾼 생산 금지 규칙 때문에 5기 데이터에는 "게이트 짓는 동안 일꾼" 겹치기가 제한된다. 이 규칙을 풀면 최적이 바뀔 수 있다.

## 6.5 학습은 질럿 2, 검증은 질럿 5: 시뮬레이터 전이 실험

6절은 질럿 5 로그로 학습하고 같은 로그로 평가한 것이다. 여기서는 **질럿 2 로그만으로 학습**하고 질럿 5 로그는 검증에만 쓴다. 코드 [offline_rl/build_sim.py](../offline_rl/build_sim.py), 결과 [results/sim_transfer_results.md](../offline_rl/results/sim_transfer_results.md), [results/state_coverage.md](../offline_rl/results/state_coverage.md), 명령열별 예측 `results/sim_pred_zealot5.csv`, 매개변수 `results/sim_params.csv`.

### 왜 표(Q)는 못 옮기는가

질럿 5 로그의 (상태, 행동) 중 질럿 2 로그에도 나온 비율:

| 추상화 | 질럿 5 (s,a) 종류 | 공유 비율 | 결정 횟수 기준 |
|---|---|---|---|
| obs_counts | 347 | 32% | 64% |
| cmd_counts | 245 | 23% | 57% |
| cmd_counts+time | 490 | 19% | 57% |
| history | 15,728 | 3% | 57% |

history 기준으로 10번째 결정까지는 일부 공유되지만 11번째부터는 0%다. 공유되는 앞부분조차 질럿 2 목표로 학습한 값이라 질럿 5에는 맞지 않는다. 옮길 수 있는 것은 "명령이 얼마나 걸리는가"의 규칙뿐이다.

### 방법: 봇 규칙을 옮긴 시뮬레이터 + 수치 적합

- 구조는 `incredibot-sct.py`의 실행 규칙에서 가져왔다. 일꾼은 미네랄 50·인구 여유 1·넥서스 큐 순차 생산, 파일런은 미네랄 100·완성 시 한도 +8, 게이트는 미네랄 150·완성된 파일런 필요, 질럿은 미네랄 100·인구 여유 2·완성된 게이트 필요·가장 먼저 비는 게이트부터 배정(봇의 '생산 재분배'), 비어 있는 게이트에 들어가면 에너지가 있을 때 시간 증폭. 명령은 직전 명령 다음 iteration부터 조건을 만족하는 첫 iteration에 실행된다.
- 수치 13개(일꾼 채취율 3구간, 첫 수입 지연, 일꾼·파일런·게이트·질럿 소요 시간, 시간 증폭 지속·회복, 건설 일꾼 채취 중단, 종료 지연)는 질럿 2 로그 997 에피소드(명령 8,346개)의 명령 실행 시각과 종료 프레임에 좌표 하강법으로 맞췄다. 적합 48초, 학습 손실 2.4 iteration.
- 적합 결과: 채취율 0.167/일꾼(13~16번째는 0.12), 일꾼 74, 파일런 115, 게이트 275, 질럿 142, 시간 증폭 창 97, 에너지 회복 273, 종료 지연 12 iteration. 게임 시간으로 환산하면 1 iteration ≈ 5.5 게임 루프(파일런 18초, 게이트 46초, 질럿 27초와 비율이 맞는다).

compact 상태 = (남은 질럿, 일꾼 명령 수, 건설 중 파일런, 완성 파일런, 건설 중 게이트, 완성 게이트, 대기 중 질럿, 미네랄//50, 시각//20).

읽는 법:
- history는 상태를 다 훑어야 수렴한다. 처음 최적에 도달한 에피소드가 상태 수의 약 16배(N=2 4만/1,058 … N=6 34만/20,381)로 늘고, N=7(3.6만 상태)부터는 40만 에피소드로 부족하다. 필요한 에피소드가 상태 수에 비례한다는 6절의 관찰이 N별로 확인됐다.
- compact는 상태가 20~50분의 1이고 N=8에서도 최적의 +5까지 간다. 하지만 N=3·5·7·8에서 정확한 최적을 놓친다. 미네랄 50, 시각 20 단위 버킷이 같은 상태에 다른 미래를 섞기 때문이다(Markov 근사의 손실).
- 즉 규모를 키우려면 compact 쪽이 맞고, 정확도는 버킷을 잘게 하거나 "진행 중 건설의 남은 프레임"을 상태에 넣어 되찾아야 한다. 다른 길은 Q 초기값을 0(낙관) 대신 시뮬레이터로 구한 어림값으로 두어 history의 탐색량을 줄이는 것이다.
- 전수 탐색이 14초에 끝나는 규모에서는 Q-learning이 전수 탐색보다 느리다. Q-learning의 의미는 전수 탐색이 불가능한 규모(공허포격기, 멀티, 명령 수십 개)로 갈 때의 방법 검증이다.

## 6.7 RL 에이전트 자체의 전이: 질럿 2로만 학습, 질럿 3~8에 학습 없이 적용

코드 [offline_rl/transfer_rl.py](../offline_rl/transfer_rl.py), 결과 [transfer_rl_results.md](../offline_rl/results/transfer_rl_results.md)(N=2~5, 미세 조정), [transfer_rl_results_pg_n8.md](../offline_rl/results/transfer_rl_results_pg_n8.md)(정책 에이전트 N=2~8).

6.6절의 표 Q는 N마다 따로 푼 것이라 "학습"이 아니라 탐색이었다. 여기서는 에이전트 하나를 **목표 2 에피소드만으로** 학습하고 목표 3~8에 그대로(zero-shot) 적용했다. 환경은 질럿 2 로그로 적합한 시뮬레이터, 보상 −프레임/100, γ=1, 행동 마스킹은 열거 규칙(게이트 상한 3). 상태는 N이 달라도 같은 입력 공간을 쓰도록 **목표 상대 특징** 19개로 두었다: 남은 질럿(명령 전), 미완성 질럿, 대기 질럿, 일꾼 명령 수, 채취 일꾼, 파일런 완성/건설 중, 게이트 완성/건설 중, 미네랄, 인구 여유, 인구 부족분, 넥서스 사용 중, 그리고 남은 질럿과 게이트·일꾼·인구 여유의 곱. 절대 시각은 큰 N에서 학습 범위를 벗어나므로 뺐다. 에이전트 4종, 3시드, 2만 에피소드.

### 해석

- **정책 경사만 옮겨졌다.** 가치 기반(선형 Q, MLP Q)은 "남은 질럿 5"의 가치 크기를 학습 범위(남은 2) 밖에서 외삽해야 하고, γ=1 부트스트랩 + 함수 근사 + 탐욕 평가가 겹쳐 불안정했다. 선형 Q는 N=2조차 못 맞춰 가치 함수가 이 특징에 선형이 아님을 보여준다. 정책은 행동의 순서만 맞으면 되므로 표현이 쉽고(선형 76개 매개변수), 볼트의 [[Sutton-정책경사-1999]]가 말하는 "가치보다 정책이 단순한 문제"에 해당한다.
- **옮겨진 것은 규칙이다.** 학습된 정책을 읽으면 "파일런 → 게이트 3개 → 질럿, 인구 부족 직전에 파일런, 일꾼은 안 뽑음"이다(일꾼 행동의 편향 −2.4~−3.0). N=2·4·5·6의 전수 최적이 일꾼을 0~1명만 쓰기 때문에 이 규칙이 그대로 맞았고, 일꾼 4명이 필요한 N=3(653)과 N=7·8에서는 +32~55로 벗어난다. 즉 질럿 2 데이터에는 "남은 질럿이 많으면 일꾼이 이득"이라는 신호가 없고, 그 신호 없이 그 부분은 일반화될 수 없다. 전이가 된 것은 맞지만 풀고자 한 교환 관계를 배운 게 아니라 N=5가 운 좋게 같은 규칙 안에 있었기 때문이다.
- **사전 학습의 쓸모는 분명하다.** 표 Q로 18만 에피소드가 들던 N=5를 사전 학습한 함수 근사가 500~4,000 에피소드에 맞춘다. 문제가 커질 때 RL이 전수 탐색을 대체하는 길은 zero-shot이 아니라 "작은 목표로 사전 학습 → 큰 목표로 짧게 미세 조정"이고, 그때 가치 기반의 불안정은 따로 잡아야 한다(학습률·목표망 주기, 또는 정책 경사로 통일).
- 실게임 검증: 정책이 낸 N=5 명령열의 로그 실제 종료는 731(시뮬레이터 731)과 739(시뮬레이터 722, 시뮬레이터가 17 낙관). 로그 최적 724와 7~15 차이로 실행 노이즈(중앙값 5, 최대 50) 수준이다.

### 사람 가이드라인과 모방학습 (2026-11-08)

"사람이 가이드라인을 먼저 설계하고 모방학습하면"에 대한 답. 모방학습(behavior cloning)은 시범을 재현할 뿐 시범보다 나아지지 않으므로 가이드라인의 품질이 상한이다. 규칙 "일꾼 w명까지(인구 부족이면 파일런) → 게이트 g개 → 질럿, 질럿 뒤 일꾼 금지"를 시뮬레이터로 재면(전수 최적 대비 프레임):

| 가이드라인 | N=2 | N=3 | N=4 | N=5 | N=6 | N=7 | N=8 |
|---|---|---|---|---|---|---|---|
| 정석: 일꾼 16, 게이트 3 | +77 | +106 | +74 | +77 | +63 | +74 | +61 |
| 절충: 일꾼 14, 게이트 3 | +36 | +31 | +49 | +36 | +26 | +49 | +20 |
| RL이 찾은 규칙: 일꾼 0, 게이트 3 | 0 | +32 | 0 | 0 | +46 | +19 | +1 |
| 일꾼 16, 게이트 2 | +77 | +106 | +74 | +172 | +102 | +161 | +163 |
| 일꾼 16, 게이트 1 | +178 | +248 | +358 | +463 | +528 | +642 | +731 |

실제 경기의 직관("일꾼은 계속")이 질럿 2~8기 단거리에서는 틀리므로, 정석을 그대로 모방하면 60~100프레임 손해가 정책에 고정된다. 사람 설계가 쓸모 있는 자리는 세 곳이다. (1) **제약(행동 마스킹)**: 열거 규칙이 이미 이것이고, 최적이 공간 안에 남는지 작은 N 전수 탐색으로 검증 가능하며 틀린 직관을 따라가지 않는다. (2) **초기화 + RL 미세 조정**: AlphaStar의 지도학습→RL 구도. 6.7절의 사전 학습 효과(18만→수천 에피소드)와 같은 이득이지만 출발점이 정답에서 멀수록 줄어든다. (3) **학습 데이터에 없는 신호 주입**: "N이 크면 일꾼 몇 명 더"는 질럿 2에 없는 신호다. 다만 그 숫자를 시뮬레이터로 확인할 수 있다면 모방보다 규칙의 매개변수(w, g)를 직접 탐색하는 편이 빠르고, 단순 규칙군은 N=3처럼 일꾼과 게이트를 섞어야 하는 경우(+31)를 표현하지 못한다. 결론: 가이드라인은 마스킹과 초기화에만 쓰고 최종 판단은 보상에 맡긴다. 후속 실험 후보: "정석 모방 → REINFORCE 미세 조정" 대 "마스킹만 두고 처음부터 REINFORCE"를 N=5·8에서 비교.

  맞추려면 reset 응답을 트리거 이후로 미루는 것을 고려한다.
- 에피소드 하나에 벽시계 8~9초(화면 켠 상태, `setLocalSpeed(0)`). GUI 를 끄면 더 빠를 것.

### 자원 채취율 측정 (2026-11-08, 문제를 하나씩: 1단계)

사용자 방향: 질럿 생산을 풀기 전에 **자원 채취만** 떼어 (1) 첫 파일런 시점, (2) 일꾼 수의 근거를 실측한다. 일꾼 상한(덩이당 2기)은
법칙이 아니라 데이터가 정할 값이므로 규칙에서 빼고 24기까지 쟀다. 자세한 표와 답은 [스타1-자원채취율-분석.md](스타1-자원채취율-분석.md).

- 첫 파일런: 목표 13기 이상이면 8기 시점이 가장 빠르다(10기면 6기, 11~12기면 7기). 둘째는 14기 시점.
- 채취율: 8기까지 일꾼당 0.046, 9~16기 한계 0.026, 17~24기 0.021 미네랄/프레임. 24기까지 계속 오르지만 한계 수익은 절반 이하.
  일꾼 1기 회수 시간 1100 → 1900 → 2400프레임. 몇 기까지 뽑을지는 목표 시각까지 남은 시간이 정한다(다음 문제).
- 프로토콜에 행동 8(대기, `frames`)을 추가(측정용, 명령열 기록에 안 들어감). 시뮬레이터 수입 상수는 실측으로 고정.
- 실행기 수정: 인구를 자기 명령 기준으로 세어 한도 초과 명령은 즉시 거부(큐 대기 유닛은 BW가 세지 않아 생긴 무한 대기 버그),
  fatal 사유 즉시 응답, 4만 프레임 상한, 에피소드 사이 속도 보통. 보정 명령열에 불가능한 것이 섞여 게임이 끝없이 돌았던 사고의 교훈.


### 사람과 함께 (라이브 어시스턴트, 2026-11-08 오후~저녁)

사용자 방향: 사람이 유닛을 조작하고, 생산 명령은 전부 AI 가. 채팅창(영문 약어)·의도 파일(나중에 음성/Dialogflow)로 목표를 넣으면
**그 시점 상태에서 최적 빌드**를 계산해 실행한다. 오후에 v1(`bridge/live_assistant.py`)을 땜질로 키우다 실게임에서 구조적 문제가
드러나 저녁에 v2 로 재설계했다. 설계·결정·상태: [스타1-라이브-빌드-재설계.md](스타1-라이브-빌드-재설계.md).

- **실게임에서 드러난 것**: 명령을 보내고 잊는 구조(놓이지 않은 건물·예약 비용·포기한 건설을 모름), 일회성 계획(유닛이 죽어도
  틀린 계획 유지), 실행기의 인구 누적 변수(죽어도 안 줄어 게이트가 놂), 건설 자리 탐색(한 칸 틈으로 드라군 갇힘 → 두 칸 규칙 →
  과해서 자리 전무 → 미탐사 타일 선택), 시야 밖 자원·타일(멀티 자리 못 찾음), 라이브에서 블로킹 step.
- **v2**: 실행기 = 감지기+구동기(`request/observe/cancel`, 요청 수명 queued→issued→done/failed, 완전한 스냅샷, 누적 변수 없음),
  계획기 = 순수 함수(스냅샷→ExpSim→명령열·예상 프레임), 제어 루프 = 틱마다 관측→편차→재계획→발행→로그(`bridge/live/`,
  `bridge/live_run.py`, 이벤트 로그 `bridge/results/live/*.jsonl`은 git 제외). 가짜 실행기 시나리오 8개 통과.
- **사용자 결정**: 명령은 친 순서대로 하나씩(합치지 않음, "z4"≠"z2,z2"); 완료는 수량 기준(사람이 지은 것도 셈; 유닛은 큐 진입,
  건물은 배치); 예비 자원(`r 200 50`)은 큐의 그 자리에서 효력, 사람이 쓰면 해제; 일꾼 목표(`wt`, 기본 기지당 16)는 상시 제약이고
  묶음 계획의 일꾼은 2배수까지; 게이트 수 상한 없음(최적이면 몇 개든); 피격 중 특별 처리 없음; 인구 부족 파일런은 목표가 있을 때만;
  일꾼 분배는 가스 3·기지당 덩이 2배수 → 3배수(완성 시 초과분 즉시 이전).
- **실행기에 추가된 것**: 드라군·하이템플러·다크템플러·어시밀레이터(가스 3기 자동)·코어·성채·아카이브·넥서스(앞마당 자리: 게임 간격 규칙,
  미탐사면 프로브 정찰 대기), 길막 방지(2칸 통로 → 1칸 → 무검사 단계적), 가스 일꾼 보호, 고갈 재배정, 200 상한, HUD, 시험용 debug
  (사람 흉내 지출·건설 취소·자기 건물 공격, 채팅 `x1~x4`).
- **미검증**: 마지막 DLL(자리 탐색 완화, 넥서스 정찰 대기, 선행 건물 대기, 이전 속도)은 빌드만 됐고 다음 게임부터. 실게임 한 판
  (질럿→드라군→템플러→멀티 + 교란)이 다음 할 일.
