# 스타1 라이브 빌드 어시스턴트 재설계 (2026-11-08)

오늘 오후 사람과 함께 플레이하며 붙인 기능은 "에피소드 실험용" 구조 위에 땜질로 쌓였다. 실게임에서 드러난 문제를 정리하고,
다음 세 목표에 맞게 구조를 다시 잡는다. 구현 전 검토용 문서다.

목표
1. **사용자가 명령을 넣는 시점의 상태에서 최적 빌드를 계산**한다. 명령은 순서대로 하나씩(순차 최적화).
2. **적 공격 같은 변수로 멈추지 않는다.** 계획이 불가능해지거나 상태가 예상과 어긋나면 그 시점부터 다시 최적 빌드를 계산한다.
3. **학습용 로그**를 남긴다. 상태·명령·계획·결과를 구조화해 시뮬레이터 적합과 이후 학습에 쓸 수 있어야 한다.

## 1. 지금 코드 검토

| 시뮬레이터 | `bridge/sc1_sim.py`, `bridge/expansion_estimate.py` | 결정론 빌드 시뮬레이터(질럿/드라군/템플러/멀티/가스). 스냅샷에서 초기화 가능 |

### 오늘 실게임에서 드러난 문제와 원인
| 증상 | 원인 | 구조적 교훈 |
|---|---|---|
| 파일런을 2~3개 더 지음 | 명령만 냈고 아직 놓이지 않은 건물·예약 비용이 스냅샷에 없었다 | 실행기의 "진행 중인 일"이 관측에 다 실려야 한다 |
| 인구 12/33 에서 파일런·게이트 헛짓 | 계획기의 행동 규칙이 "새 게임" 가정 | 계획은 항상 현재 상태에서 출발해야 한다(규칙·초기화 모두) |
| 게이트 7개가 놀고 파일런만 늘어남 | 실행기의 인구 누적 변수가 유닛이 죽어도 줄지 않음 | 실행기는 내부 상태를 누적하지 말고 매번 게임에서 다시 계산한다 |
| 성채 명령은 나갔는데 건물이 없음 | 갇힌 프로브를 반복 선택, 40회 뒤 조용히 포기. 클라이언트는 모름 | 명령의 수명(수락→진행→완료/실패)이 보여야 한다 |
| 질럿 3기마다 650프레임 정지 | 위 인구 버그 + 거부 시 같은 계획 반복 | 거부·실패는 즉시 다시 계획의 입력이 돼야 한다 |
| 유닛 갇힘 | 한 칸 틈을 길로 침 (드라군은 못 지남) | 배치 규칙은 유닛 크기를 고려한 2칸 통로 |
| 멀티 자리 못 찾음·위치 엉망 | 시야 밖 자원·타일을 못 봄, 간격 규칙 어림 | 지형·초기 자원 데이터로 판정, 게임 규칙을 그대로 쓴다 |
| 적 공격 뒤 멈춤 | 계획이 명령 시점에 한 번 계산되고 끝. 실행 중엔 거부가 올 때만 반응 | **관측 → 편차 감지 → 재계획**이 매 틱 돌아야 한다 |

핵심은 두 가지다. (1) 명령을 보내고 잊는 구조(fire-and-forget)라 실행기 안에서 벌어지는 일을 어시스턴트가 모른다.
(2) 계획이 일회성이라 세계가 바뀌면 틀린 계획을 끝까지 밀고 간다. 라이브 모드에 블로킹 `step`을 그대로 쓴 것도 문제다.
한 명령이 끝날 때까지 다른 일을 못 한다.

## 2. 설계 원칙

- **실행기 = 감지기 + 구동기.** 계획하지 않는다. 명령은 ID 가 있는 비동기 요청이고 수명을 보고한다. 관측은 언제나 완전하다.
- **계획기 = 순수 함수.** (관측 스냅샷, 목표 큐, 제약) → 다음에 낼 명령열과 예상 시간표. 상태를 갖지 않는다.
- **제어 루프 = 매 틱 반복.** 관측 → 의도 반영 → 편차 검사 → 필요하면 재계획 → 지금 낼 수 있는 명령 발행 → 로그. 어디서도 막히지 않는다.
- **결정론 실험 모드는 그대로 둔다.** 에피소드·프레임 블로킹·데이터셋은 시뮬레이터 적합과 탐색에 계속 쓴다. 라이브는 별도 경로다.

## 3. 새 구조

```
[사람] 채팅 / 의도 파일(음성·Dialogflow) ──► intents.py ──► 목표 큐
                                                          │
         ┌───────────────── controller.py (틱 = 12프레임) ─┴──────────────────┐
         │ observe() ──► 편차 검사 ──► planner.plan(snapshot, goal, constraints) │
         │     ▲                                   │                            │
         │     │                             다음 명령 발행(비동기 request)        │
         │  eventlog.py ◄── 모든 단계 기록 ◄────────┘                            │
         └──────────────────────────────┬───────────────────────────────────────┘
                                        ▼ TCP(JSON 줄) v2
                         BuildExecutor.dll: request / observe / 자동 기능 / HUD
```

### 3.1 실행기 (BWAPI 모듈) — 프로토콜 v2
- `request {id, action, args}` → 즉시 `{accepted|rejected, reason}`. 실행은 실행기가 책임진다.
  - 생산: 큐에 들어가면 `done`. 건설: **건물이 놓이면** `done`. 그 전까지 `in_progress`(프로브·자리·재시도 수 포함).
  - 실패(`failed`)는 명시 사유와 함께: `supply_maxed`, `no_site`, `no_geyser`, `abandoned(n회)`, `requires:X`.
  - 재발행 규칙: 24프레임 간격, 실패한 프로브 제외, 자리 재탐색, 상한 200회. 포기도 실패 보고다.
- `observe` → 완전한 스냅샷 한 장:
  자원(미네랄·가스·**예약분**), 인구(게임값 + 큐 대기분, 한도), 일꾼(미네랄/가스/건설/유휴), 기지(넥서스 완성·건설 중·자리),
  건물별(완성·건설 중 남은 시간·명령됨 경과), 생산 큐(건물별 길이·남은 시간), 요청 목록(상태), 위협(본진 근처 적 유닛 수,
  마지막 피격 프레임, 잃은 유닛·건물 수), 프레임.
- 라이브 모드에서는 어떤 메시지도 게임을 멈추지 않는다. 실험 모드(`reset`/`step`)는 v1 그대로.
- 내부 누적 상태 금지: 인구·예약은 매 호출 게임 상태에서 계산. 유일한 영속 상태는 요청 목록과 건설 감시.
- 자동 기능은 유지(일꾼 배정·고갈 재배정·가스 3기·2칸 통로 배치·앞마당 자리). 전부 결정론 규칙이고 문서화한다.

### 3.2 계획기
- 입력: 스냅샷, 목표 하나(유닛·수 또는 건물·수), 제약(예비 자원, 일꾼 목표, 기지당 일꾼 상한).
- 출력: 명령열과 각 명령의 예상 실행 프레임, 예상 완료 프레임, 가정(수입률·가스율).
- 방법: `ExpSim.from_snapshot` + 계층화 빔(지금 것). 규칙은 스냅샷 기준(`make_allowed_from`)만 남기고 "새 게임" 규칙은 실험 모드로 격리.
- 1초 안에 끝난다. 틱마다 돌려도 되지만 보통은 편차가 있을 때만 다시 돈다.

### 3.3 제어 루프 (어시스턴트)
틱마다:
1. `observe` → 스냅샷. 의도 입력(채팅·파일) 반영. 예비·일꾼 목표 갱신.
2. **편차 검사** — 다음 중 하나면 재계획:
   - 요청 실패/포기 보고가 있음
   - 예상 실행 프레임보다 N(예: 300)프레임 이상 늦어짐 (자원·인구가 예상과 다름)
   - 건물·유닛 손실(잃은 건물 수 증가), 본진 피격 플래그
   - 사람이 자원을 썼거나 건물을 지음 (관측과 계획 가정의 괴리)
   - 목표가 불가능(인구 200, 간헐천 없음) → 목표를 실패로 표시하고 다음 목표
3. 재계획이면 현재 목표를 스냅샷에서 다시 풀고 명령열을 교체. 이미 보낸 요청은 그대로 둔다(실행기가 책임).
4. 명령열의 머리부터, 지금 조건이 되는 것만 `request` 로 보낸다. 조건은 실행기가 판정하므로 보내고 상태를 본다.
5. 목표 완료 판정: 유닛은 큐 진입, 건물은 놓임(사용자 결정). 완료면 다음 목표(예비 적용 포함).
6. 이벤트 로그 기록. HUD 갱신(현재 목표·진행·다음 명령·대기 큐·예비·경고).

적 공격 처리: 멈추지 않는다. 손실과 피격은 편차로 들어가 재계획을 일으킬 뿐이다. 전투는 사람 몫. 단, 피격 중에는 멀티 같은
원거리 건설 요청을 보류하는 선택지를 둘 수 있다(옵션).

### 3.4 목표 의미(사용자 결정 유지)
- 큐는 친 순서. 목표 하나 = "지금 상태에서 가장 빨리". 합치지 않는다.
- 목표 완료 = 유닛은 생산 큐 진입, 건물은 배치. 그 상태에서 다음 목표를 계산한다. 건물은 일꾼에게 명령만 나간 상태(pending)를
  완료로 세지 않는다. 대신 계획할 때는 명령된 건물을 이미 있는 것으로 보고 다시 짓지 않는다(2026-11-08 밤 수정, 10절).
- 예비 자원은 큐의 그 자리에서 효력. 사람이 그 돈을 쓰면 해제.
- 일꾼 목표는 상시 제약(기본 기지당 16, `wt`로 변경). 목표 계획은 그 이상 일꾼을 넣지 않는다.

## 4. 학습용 로그

`bridge/results/live/<게임ID>.jsonl` 에 틱 단위 이벤트:
- `observe`: 스냅샷 전체(위 3.1). 틱마다.
- `intent`: 입력 원문·출처·해석 결과.
- `plan`: 목표, 명령열, 예상 프레임, 계획기 가정, 계산 시간, 재계획 사유.
- `request`/`result`: 명령 ID·행동·보낸 프레임·수락 여부·완료/실패 프레임·사유.
- `deviation`: 감지 종류와 수치(예상 vs 실제).
- `game_end`.
쓰임: (1) 시뮬레이터 적합(예상 프레임 vs 실제), (2) 편차 통계(어떤 변수가 계획을 깨는가), (3) 나중에 상태→행동 데이터셋.
실험 모드의 `sc1_dataset.jsonl`(결정론, 명령열→궤적)은 그대로 둔다. 두 로그는 같은 스냅샷 형식을 쓴다.

## 5. 정리와 범위

- 다시 쓰는 것: `live_assistant.py` → `bridge/live/{intents,planner,controller,eventlog,hud}.py`. 실행기의 메시지 처리(`request/observe`)와
  요청 수명 관리. `env.py`에 v2 클라이언트(`LiveClient`) 추가.
- 그대로 두는 것: 시뮬레이터, 빔 탐색, 자동 기능 규칙, 실험 모드(v1), 데이터셋·측정 도구.
- 버리는 것: 라이브에서의 블로킹 `step`, 묶음 합치기, 어시스턴트 쪽 "내가 낸 건설 명령 추적"(실행기가 보고하므로 불필요), 인구 누적 변수.

## 6. 구현 순서와 검증
1. 실행기 v2: `observe` 스냅샷 완성 + `request` 수명 보고. 실험 모드 회귀 시험(10회 결정론 4557) 유지.
2. `LiveClient` + 가짜 실행기(파이썬)로 제어 루프 단위 시험: 거부·포기·손실·사람 소비 시나리오에서 재계획이 도는지.
3. 계획기 인터페이스 정리(스냅샷 전용 규칙), 예상 프레임 출력.
4. 이벤트 로그 + 재생 도구(로그로 그 판을 되짚어 계획 편차를 보는 스크립트).
5. 실게임: 질럿→드라군→템플러→멀티 순서로 한 판, 중간에 일부러 건물을 부수고 자원을 써서 재계획이 도는지 확인.

## 7. 열린 질문
- 틱 간격 12프레임(0.5초)이면 계획기 1초가 틱을 넘을 수 있다. 계획은 별도 스레드에서 돌리고 결과를 다음 틱에 반영할지.
- 사람이 직접 지은 건물·뽑은 유닛을 목표 달성으로 칠지(예: 사람이 성채를 지으면 계획의 성채를 건너뜀) — 지금은 선행 건물로만 인정.
- 앞마당 어시밀레이터·둘째 기지 가스, 두 기지 이상의 일꾼 분배 규칙.
- 피격 중 건설 보류 옵션의 기본값.

## 8. 결정 기록 (2026-11-08, 사용자)
- **사람이 지은 건물·뽑은 유닛도 목표 달성으로 친다.** 목표 완료는 "누가"가 아니라 **수량**으로 판정한다(기준 시점 대비 건물 수·유닛 수).
  사람이 성채를 지은 뒤 재계산하면 계획에서 성채가 자연히 사라지므로, 수량 기준이 아니면 목표가 영영 안 끝난다.
- **피격 중 특별 처리 없음.** 계획은 멈추지 않는다. 사람이 `cancel` 뒤 다시 명령하면 된다.
- **일꾼 분배 규칙을 넣는다.** 가스는 어시밀레이터당 3기 유지, 미네랄은 기지마다 덩이당 2배수를 채운 뒤 3배수까지. 새 일꾼은
  비율(일꾼/덩이)이 가장 낮은 기지로, 3배수를 넘는 기지의 일꾼은 2배수 미만인 기지로 옮긴다.

- **일꾼 규칙 개정 (2026-11-08 밤).** 일꾼 목표는 덩이 3배수(완성 기지마다 덩이 × 3 + 완성 어시밀레이터마다 3). 각 기지는 2배수를 남기고
  넘는 일꾼을 2배수 미만인 멀티로 옮긴다(그다음 3배수 넘는 기지 → 3배수 미만 기지). 새 일꾼은 2배수 미만 기지(가까운 곳 먼저) → 3배수 미만 →
  가장 가까운 기지 순으로 보낸다. 일꾼 생산 넥서스는 큐가 짧은 곳, 같으면 일꾼이 필요한 기지의 넥서스. 고르게 나누기(1배수부터)는 택하지 않았다.

## 10. 개선 반영 (2026-11-08 밤)

실게임 검토 뒤 사용자 결정: **순서 고정 유지**(병렬 목표 없음), 아래 개선을 넣고 커밋.

1. **건물 완료 = 배치.** `Goal.progress` 는 놓인 수(완성 + 건설 중)만 센다. 기준값과 계획용 수(`Goal.committed`)는 명령된 건물까지
   센다. 그래서 명령만 나간 건물로 목표가 끝나지 않고, 일꾼이 가는 동안 같은 건물을 또 계획하지도 않는다. 목표 시작 때 이미 오던
   건물(인구 유지 파일런 등)은 이 목표 몫이 아니다. 그 건물이 포기되면 이 목표가 하나 더 짓는다(드문 경우, 수량 규칙의 대가).
2. **건물·업그레이드 목표는 주기(600프레임)·늦어짐 재계획을 하지 않는다.** 실행기가 순서대로 처리 중인 요청을 취소·재요청하던
   낭비였다. 대신 "낸 요청이 다 끝났는데(실행·실패) 몫이 남음"을 모든 목표에서 본다(병력은 다음 몫, 건물은 놓인 건물이 부서졌거나
   명령된 건물이 사라짐). 요청 실패와 건물 손실 재계획은 그대로. 병력·일꾼 목표는 주기·늦어짐도 그대로 본다.
3. **제어 루프 상태 저장·복원.** 큐·현재 목표(의도·기준값·재계획 수·실패 수·대기 여부)·예비·일꾼 목표를 `bridge/results/live_state.json`
   에 쓴다(내용이 바뀌었거나 240프레임마다). 다시 켜면 스냅샷의 `game_id` 가 같을 때만 이어 받고(없으면 저장 프레임부터 2400프레임 안),
   첫 틱에 지금 상태에서 다시 계획한다. 이어 받으면 오프닝·시작 목표를 다시 넣지 않는다(재시작 때 드라군 목표가 둘 생기던 실수).
4. **시험 지출(`x1`, debug spend)은 예비를 무시한다.** 사람은 예비를 지키지 않으므로, 예비를 지키는 시험 지출로는 "사람이 쓰면 해제"를
   확인할 수 없었다.
5. **로그 재보정** (`bridge/live/refit.py`). 이벤트 로그에서 건물 이동 시간(일꾼에게 건설 명령 → 배치), 가스 채취율, 미네랄 모형 오차,
   계획 지연을 잰다. 계획기 상수 = 이동 중앙값 + BW 건설 시간. `live_run` 은 게임이 끝날 때마다 최근 40개 로그로 다시 재고
